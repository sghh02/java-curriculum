# AI時代のJava学習法（接続編）

この章は、共通土台「AI時代の思考OSアップデート」を完了した人向けの接続章です。
ここでは、作成済みの日本語設計書を Java / Spring Boot 実装に翻訳する進め方を固定します。

---

## 前提

- 「AI時代の思考OSアップデート」を完了している
- `thinking-os-canvas.md`（課題設定キャンバス）がある
- `design-spec.md`（日本語設計書）がある
- `design-change-log.md`（仕様変更履歴）がある

## この章の役割

この章では次の1点に絞ります。

- 設計書を、Java学習の実装タスクへ変換する

共通土台で学んだ分解・検証・再設計を、Javaカリキュラム全体で再利用します。

## 設計書をJava実装へ翻訳する5ステップ

1. `thinking-os-canvas.md` と `design-spec.md` を見て、最優先ユースケースを1つ選ぶ
2. ユースケースを Java の責務に分ける
3. AIに「既存プロジェクト前提」で実装順序を作らせる
4. 実装後、`thinking-os-canvas.md` / `design-spec.md` と差分を照合して修正する
5. 仕様変更時は `design-change-log.md` を更新する

## 責務分解の目安

| 設計書の記述 | Java / Spring Bootでの主な置き場 |
|---|---|
| 業務ルール | `Service` |
| 入出力仕様 | `Controller` / DTO |
| 永続化ルール | `Repository` / Entity |
| 条件分岐 | `Service` メソッド |
| 例外時の挙動 | 例外クラス / ハンドラ / テスト |

## AIに依頼するときの型

```text
【前提】
共通土台で作成した design-spec.md を Java 実装に落としたい。

【対象機能】
（例）学習タスクを保存・検索するAPI

【既存コード】
- Controller: ...
- Service: ...
- Repository: ...

【依頼】
既存設計を崩さず、必要な修正ファイルと実装順序を先に提案して。
次にテスト観点を列挙してから、コード案を出して。
```

## よくある失敗

- 仕様を固定せずにコード生成を始める
- Entity/DTO/Serviceの責務が混在する
- 例外パスとテストを後回しにする
- AI提案を採用した理由が説明できない

## 失敗時の戻り先

詰まったら、共通土台の次を見直してください。

1. Unit 2: 課題設定キャンバスが弱い
2. PHASE 1: 要件分解が不足している
3. PHASE 2: 技術判断の根拠が不足している
4. PHASE 3: 条件分岐の定義が不足している
5. PHASE 4: 変更時の差し替え設計が弱い
